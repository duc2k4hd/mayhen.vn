Không chỉ tạo một file hướng dẫn chung.
18.1. Thư mục chuẩn
/.agents/skills/
Mỗi skill có:
/.agents/skills/[skill-name]/SKILL.md
Có thể thêm tài liệu hỗ trợ trong cùng thư mục khi thực sự cần.
Tạo:
/AGENTS.md
làm file điều phối quy tắc chung cho các coding agents.
Không coi các file skill là tài liệu viết một lần rồi bỏ. Phải duy trì chúng phù hợp với code thực tế.
18.2. Danh sách skill bắt buộc
Skill 1 — mayhen-project-architecture
Quy tắc kiến trúc Laravel, module, dependency, file structure, boundaries.
Skill 2 — mayhen-brand-design
Nhận diện thương hiệu, màu sắc, typography, spacing, visual direction.
Skill 3 — mayhen-ui-ux
Quy trình thiết kế page, responsive, user flows, accessibility.
Skill 4 — mayhen-blade
Quy tắc viết Blade, layout, component, tách file, escape và tái sử dụng.
Skill 5 — mayhen-css
Quy tắc CSS thuần, bắt buộc prefix, token, responsive, tránh conflict.
Skill 6 — mayhen-javascript
Quy tắc JavaScript thuần, module, DOM, events, fetch, cleanup, validation.
Skill 7 — mayhen-animation
Animation system, motion design, performance, reduced motion, animation QA.
Skill 8 — mayhen-invitation-templates
Template engine, section schema, components, versioning, preview, publication.
Skill 9 — mayhen-database
Database design, relationships, constraints, migrations, indexes, schema review.
Skill 10 — mayhen-laravel-backend
Controller, Request, Model, Service, Policy, Jobs, Events, transactions.
Skill 11 — mayhen-auth-security
Authentication, authorization, sensitive data, sessions, upload security.
Skill 12 — mayhen-payments
Orders, payments, webhook verification, idempotency, reconciliation, refunds.
Skill 13 — mayhen-guest-rsvp
Guest groups, invitations, links, RSVP, privacy, exports.
Skill 14 — mayhen-admin
Admin modules, UI, CRUD, permissions, validation, audit.
Skill 15 — mayhen-partners
Studio and reseller modules, commission and tenant-like data ownership.
Skill 16 — mayhen-seo
Technical SEO, content, metadata, sitemap, canonical, structured data.
Skill 17 — mayhen-performance
Image optimization, animation budgets, caching, Core Web Vitals.
Skill 18 — mayhen-testing-quality
Test strategy, acceptance criteria, browser review, temporary test cleanup.
Skill 19 — mayhen-deployment
Environment, deployment, backups, rollback, monitoring.
Skill 20 — mayhen-code-review
Checklist kiểm tra file thay đổi, duplicate logic, security, naming, regression.
18.3. Cấu trúc nội dung mỗi SKILL.md
Mỗi skill phải có:
Skill name.
Purpose.
Scope.
Applicable paths.
Mandatory rules.
Forbidden patterns.
Workflow.
Naming conventions.
Architecture conventions.
Example file structure.
Quality checklist.
Testing checklist.
Common mistakes.
Definition of Done.
Dependencies on other skills.
Rules for updating the skill itself.
Không viết skill chung chung chỉ có vài câu.
Không copy toàn bộ AGENTS.md vào mọi skill.
Các skill phải có trách nhiệm rõ ràng, hạn chế trùng lặp.
18.4. Quy tắc kích hoạt skill
Trong AGENTS.md, xây dựng cơ chế hướng dẫn:
Sửa CSS → đọc mayhen-css, mayhen-brand-design, mayhen-ui-ux.
Sửa animation → đọc mayhen-animation, mayhen-performance.
Sửa Blade → đọc mayhen-blade, mayhen-css.
Sửa migrations → đọc mayhen-database.
Sửa payment → đọc mayhen-payments, mayhen-auth-security.
Sửa template → đọc mayhen-invitation-templates, mayhen-animation.
Sửa SEO → đọc mayhen-seo.
Sửa Admin → đọc mayhen-admin.
Deploy → đọc mayhen-deployment.
Review code → đọc mayhen-code-review.
Nếu hệ thống coding agent không tự động nhận diện thư mục skills, phải có hướng dẫn rõ trong AGENTS.md để agent đọc thủ công đúng file trước khi làm việc.
18.5. Quy tắc duy trì
Khi quyết định kiến trúc thay đổi:
Xác định skill liên quan.
Kiểm tra quy tắc hiện tại.
Đề xuất thay đổi.
Cập nhật tài liệu khi được chấp thuận.
Kiểm tra ảnh hưởng tới các skill khác.
Không được tự sửa skill chỉ để hợp thức hóa code sai vừa viết.

PHẦN 19. QUY TẮC TEST, FILE TẠM VÀ XÓA FILE
Đây là yêu cầu nghiêm ngặt.
19.1. Không được tự ý xóa file
Trước khi xóa file phải biết:
File do ai tạo.
File thuộc nhiệm vụ nào.
File có đang được tham chiếu không.
File có tồn tại trước phiên làm việc không.
File có chứa dữ liệu thật không.
Việc xóa có ảnh hưởng nơi khác không.
Không xóa file chỉ vì cho rằng nó không còn cần thiết.
Không chạy lệnh xóa hàng loạt, reset hoặc clean trên repository khi chưa kiểm tra phạm vi.
Không sử dụng các lệnh nguy hiểm để sửa nhanh tình trạng Git.
19.2. Quy tắc file test tạm
Trong quá trình kiểm thử, coding agent có thể tạo file tạm thuộc phạm vi nhiệm vụ.
Bắt buộc:
Ghi nhận danh sách file test tạm được tạo.
Thực hiện kiểm thử.
Kiểm tra kết quả.
Ghi kết quả và những lỗi phát hiện.
Xóa các file test tạm do chính agent tạo sau khi hoàn thành.
Kiểm tra lại Git diff và trạng thái repository.
Không để sót ảnh screenshot debug, HTML demo, test output hoặc file log tạm không cần thiết.
Không được tự ý xóa file test hoặc file khác vốn đã tồn tại trước nhiệm vụ.
Nếu có bộ kiểm thử regression được dự án chủ động lưu giữ lâu dài, phải phân biệt rõ với file test tạm. Khi yêu cầu không lưu file test mới được áp dụng, chỉ xóa những file mới do agent tạo sau khi đã kiểm thử và ghi nhận kết quả; không phá hủy bộ kiểm thử gốc.
19.3. Kiểm thử bắt buộc
Sau mỗi hạng mục:
Kiểm tra syntax.
Kiểm tra route.
Kiểm tra validation.
Kiểm tra database.
Kiểm tra quyền truy cập.
Kiểm tra UI.
Kiểm tra responsive.
Kiểm tra lỗi console.
Kiểm tra CSS conflict.
Kiểm tra JS runtime.
Kiểm tra tương tác.
Kiểm tra dữ liệu thật/giả.
Kiểm tra security nếu liên quan.
Kiểm tra regression các module dùng chung.
Không tuyên bố PASS khi chưa chạy kiểm thử.
Nếu môi trường không có khả năng mở browser hoặc chạy một bài test cụ thể, ghi rõ "chưa kiểm thử".
19.4. Quy tắc sau mỗi nhiệm vụ
Chỉ báo cáo:
Chức năng hoàn thành.
Kết quả thực tế.
File đã tạo.
File đã sửa.
File test tạm đã xóa.
Migration đã thêm hoặc thay đổi.
Các kiểm thử đã chạy.
Lỗi còn tồn tại.
Rủi ro.
Công việc tiếp theo.
Ưu tiên cung cấp bản tóm tắt thay đổi và không gửi lại toàn bộ file không thay đổi.

PHẦN 24. QUY TẮC CODE REVIEW

A. Kiến trúc
Có đúng cấu trúc Laravel không?
Có trùng logic không?
Có tách trách nhiệm hợp lý không?
Có tạo abstraction thừa không?
B. Blade
Có dùng layout/component phù hợp không?
Có chứa CSS/JS inline không?
Có escape output đúng không?
Có semantic HTML không?
C. CSS
Tất cả class có prefix chưa?
Có selector gây ảnh hưởng trang khác không?
Có CSS trùng không?
Có responsive đầy đủ không?
Có !important không cần thiết không?
D. JavaScript
Có sử dụng thư viện bị cấm không?
Có xử lý lỗi không?
Có event listeners trùng không?
Có memory leak không?
Có lỗi DOM khi phần tử không tồn tại không?
Có ảnh hưởng hiệu suất không?
E. Database
Có thêm migration không cần thiết không?
Có thể tái sử dụng bảng/cột hiện tại không?
Foreign key và index đã đúng chưa?
Migration an toàn chưa?
F. Security
Có kiểm tra authorization không?
Có validate input không?
Có lọt dữ liệu nhạy cảm không?
Có vấn đề upload/XSS/CSRF không?
G. Business
Chức năng có thực sự giải quyết nhu cầu người dùng không?
Có thêm phức tạp không cần thiết không?

PHẦN 27. YÊU CẦU THỰC HIỆN NGAY SAU KHI NHẬN PROMPT

KHÔNG BẮT ĐẦU VIẾT HÀNG LOẠT CODE NGAY.
Trước tiên, hãy thực hiện theo thứ tự:
Bước 1. Kiểm tra repository
Đọc toàn bộ cấu trúc liên quan, công nghệ, tình trạng Git, các file quy tắc, migrations và mã nguồn hiện có.
Không tự thay đổi hoặc xóa file trong bước khảo sát.
Nếu repository chưa tồn tại, ghi nhận đây là dự án mới.
Bước 2. Nghiên cứu đối thủ

3. Thứ tự mình khuyên bạn thực sự triển khai
Mặc dù prompt đã liệt kê đầy đủ chức năng, mình nghĩ cần ưu tiên bốn trụ cột sau để Mây Hẹn không bị biến thành một dự án rất lớn nhưng mãi chưa bán được sản phẩm.
Ưu tiên 1 — Giao diện và 3 mẫu thiệp xuất sắc
Trang chủ đẹp, thư viện mẫu có bố cục tốt và 3 thiệp mẫu với animation hoàn chỉnh. Đây là thứ khách hàng nhìn thấy đầu tiên và cũng là lý do quan trọng để họ sẵn sàng trả tiền.
Ưu tiên 2 — Khách tự tạo thiệp thật dễ
Editor nhanh, xem trước trực tiếp, chỉnh sửa trên điện thoại, lưu nháp và xuất bản. Không cần làm công cụ thiết kế tự do phức tạp ngay lập tức.
Ưu tiên 3 — Gửi thiệp và quản lý khách mời
Link cá nhân hóa, Zalo, QR, RSVP, lời chúc. Đây là các tính năng thực tế khiến khách dùng thiệp online thay cho một ảnh thiệp tĩnh.
Ưu tiên 4 — Thanh toán và vận hành
Có gói trả phí, xác minh giao dịch, quản lý thiệp và Admin đủ dùng để bắt đầu bán hàng. Sau khi có khách thật mới đầu tư sâu vào studio, AI và quản lý bàn tiệc.
Một lưu ý kỹ thuật mình muốn nhấn mạnh: hệ thống template và cấu trúc dữ liệu thiệp nên được thiết kế đúng ngay từ đầu, vì chúng quyết định khả năng mở rộng hàng trăm mẫu sau này. Ngược lại, các tính năng như AI, xếp bàn tự động hay white-label có thể để sau mà không ảnh hưởng nhiều nếu kiến trúc lõi đã được chuẩn bị.
Prompt trên cũng đã quy định rõ việc không xóa file gốc và dọn file test tạm do agent tạo. Điều này giúp tránh tình trạng một coding agent chạy lệnh dọn dẹp rồi vô tình xóa mất code hoặc bộ kiểm thử sẵn có.
Hướng mình đánh giá phù hợp nhất cho mayhen.vn: Đầu tư rất mạnh vào chất lượng thiết kế thiệp, animation và trải nghiệm mobile trước, sau đó mới mở rộng chức năng quản lý đám cưới. Դա mới là cách tạo ra sự khác biệt mà khách hàng có thể cảm nhận ngay khi mở một tấm thiệp.
